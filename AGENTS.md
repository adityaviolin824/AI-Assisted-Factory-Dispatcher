# Project instructions

## Working safely

- Never expose API keys or other secrets. If one appears, stop and tell the user without repeating its value.
- Keep new code and notebooks inside this project, using its existing `backend/` and `frontend/` layout. Paths in this file are relative to this repository root; do not create an extra nested `CODES/` folder. Preserve existing work unless a change is requested.
- Do not run Git commands unless the current directory is confirmed to be inside this repository. Never target a parent, sibling, or unrelated directory. Never use destructive Git commands such as reset, clean, or force push.
- Do not use `rm`, sudo, admin access, migrations, or other hard-to-reverse commands without explaining the impact and warning the user repeatedly first.
- Never install packages or tools globally on this Mac. For Python, use a project-local `.venv` managed by `uv`; use `uv run` and `uv add`, not system Python or global pip. Do not install dependencies until they are needed and requested. Avoid global npm and Homebrew installs too.
- Work in small steps and validate each step. Before fixing a bug, identify and prove its root cause with evidence, checking one hypothesis at a time.
- Prefer the simplest reliable implementation: short, readable code, clear names, and concise docstrings. In experiment notebooks, add explanatory comments about what each step does and why; avoid comments that merely repeat the code.
- Keep code examples and displays easy for a beginner to understand and maintain. Prefer direct code and plain output over extra helpers, abstractions, or interactive display features when they do not add necessary value.
- Do not add debugging code, logging, retries, or exception handling for hypothetical problems. Add them only when an observed failure or an expected input boundary requires them, and remove temporary debugging code after verification.
- Check current official documentation before using library APIs. Do not invent commands, paths, packages, or project facts.
- When changing code, report the exact files and edits and explain what was validated. Do not use emojis in code or Markdown.

## Project rules

- **Current frontend priority (21 October 2026):** follow [Project handoff](PROJECT_HANDOFF.md). Design the frontend, connect it to the existing API and verify functionality through dispatcher review. Dedicated backend results/evaluation work comes later. Docker, containers, Compose and deployment are at the absolute end and must be ignored for now; do not treat them as prerequisites. Keep secret protection, no-Git instructions and no global/system installations in force.
- **Both core interfaces are required:** Operations chat and Dispatcher belong in the same Next.js application. Use `backend/experimentation_notebooks/mock_frontend/` as the chat behavior reference and include the small API bridge for message/history/snapshot capture and explicit pipeline handoff. Do not downgrade chat to a disabled/quote-only placeholder because the endpoints are missing. Use the user-invoked Frontend App Builder skill and [frontend design brief](frontend/FRONTEND_PLAN.md#3a-visual-direction-for-both-core-interfaces): sophisticated, distinctive dark themes; no generic AI templates, purple accents or decorative gradients; no prescribed palette/font/layout in the plan. Paid execution still needs separate authorization.
- **Latest dispatcher interaction (21 October 2026):** unfinished choices stay in page memory; no per-click mutation/recalculation, database/checkpoint/draft write or autosave. The dispatcher completes the set and clicks **Approve all** once; Python keeps his destinations fixed, rearranges the flexible work, saves immediately and shows the final table with what changed and why. No mandatory second approval. This supersedes the old per-edit checkpoint/empty-approval product design, which current code still implements. Update that contract separately when implementation is requested; do not claim these documentation edits changed runtime behavior. The goal is an assignment MVP dispatch table, not live factory operations.
- Keep the supplied documents in `reference-documents/`, copied inputs in `backend/data/`, and `harness/simulate.py` unchanged. Run extra evaluation beside the simulator. Do not edit external project source materials.
- Before making a broad decision about the app's scope, architecture, workflow, features, or evaluation, read `reference-documents/Factory_Primer.md` and use it as the primary description of the Track 2 problem. Explain how the decision helps the dispatcher determine whether a workshop can make a batch, can take it given its capacity and queue, and is allowed to take it.
- Check broad plans against the Sprint Reviews and Track 2 evaluation requirements in [Project plan](docs/project-plan.md). Treat reference documents as project context; the user's current request and these working-safety rules still govern what actions to take.
- Prototype backend scheduling changes in notebooks first. Intake, processing, routing, allocation and dispatcher review are modularized, `backend/app_full_pipeline/` runs them through the review pause, `backend/eval_harness/` scores allocation with the harness, and FastAPI serves saved runs/reviews. The Next.js shell and read-only dispatcher now exist; Operations chat, visual design and the needed chat/batch API contracts remain work to complete. Do not scaffold over the existing frontend. Follow [backend instructions](backend/AGENTS.md) for backend changes.
- LLMs may interpret requests and explain recorded decisions. Deterministic code must calculate dates, queues, costs, scores, rankings, and allocations.
- Enforce workshop status, category compatibility, batch caps, and request constraints in code before selecting a workshop. The dispatcher's own workshop choice is the exception: the dispatcher decides, so the choice is always used, even when late or past its deadline, and any rule it breaks is recorded in its reason (decision of 20 October 2026). Clarify missing facts and decline unsupported questions rather than inventing answers.
- Prioritize avoiding lateness and reducing delivery time for most tasks. Delicate or expensive work may prioritize low defect rates more strongly. Preserve current policy behavior while evaluating changes; do not invent task-value data or quality weights. Software/API latency is a separate measure.
- Keep the historical 120-order harness replay distinct from live dispatch: the harness includes completed orders. The notebook experiment does not establish a live status policy; a future live flow must check current order status.
- Report the harness's six official metrics unchanged. Label tardiness-severity measures as separate external metrics, and evaluate decisions and explanations separately on the 30 requests.
- Favor depth: a valid, explainable, measured dispatch flow comes before extra channels, voice, vector retrieval, or a broad interface.
- Document every architectural decision with its reason, relevant alternatives, assumptions, and expected effect on correctness, latency, or evaluation. Give every functionality a clear purpose and explain that purpose aloud in project discussions and presentations so the design can be defended.
