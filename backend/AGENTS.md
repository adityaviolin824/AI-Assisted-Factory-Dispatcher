## Processing rules to preserve

- Keep message IDs, extracted item IDs, task IDs and order IDs separate. An order ID alone does not prove that two requests are the same task.
- Extract each target message once. Earlier messages may supply context without being extracted again. Save every item from a message before marking it processed.
- Check original quotations, repeated items and written order-ID coverage before accepting a batch. Schema checks alone do not prove that the model understood the message.
- Keep independent requests and information questions separate. Attach a follow-up only when its original text supports the relationship; keep uncertain links for review.
- Adding a correction changes the task version and clears its earlier verification. Verify the current version with all its recorded evidence.
- Keep extraction and verification in bounded batches. Do not silently discard candidates or truncate evidence to fit a limit.
- Keep current scheduling fields separate from historical quotations. Missing facts, unresolved questions, unsupported conditions and omitted workshop instructions block readiness.
- Only delivery wording sets a deadline; dispatch timing such as "send out today" never does. Without a chat deadline, the CSV due date applies. Python, not the model, turns relative delivery words into dates from `message_date`, using the fixed list and conventions in the [system design](../docs/system-design.md#verify-before-allocation); other relative words ask for a calendar date. Never estimate a quantity: identify the order and use its CSV quantity (decisions of 18 October 2026). A piece count written for the order that differs from the CSV blocks readiness and asks which applies; the CSV quantity is never replaced (decision of 19 October 2026, after Test 8). When no deadline is selected, Python asks which written date applies if the evidence has a written date or time word outside a dispatch clause; that check never sets or removes a deadline (decision of 19 October 2026).
- Preserve checkpoints and recorded model responses. First match every verification answer to its requested task/version; an unmatchable response sends the requested batch to review. Otherwise accept valid assessments independently and record expected interpretation failures for review. API, file and programming errors must remain visible execution failures.
- Allocation plans one explicitly named run: the run just processed, or a saved run folder given to `run_allocation.py`. It always plans the verified tasks; when processing is incomplete, the plan is marked partial and lists every input without an outcome. Complete runs are planned exactly as saved. An unresolved input never holds a task (decision of 15 October 2026):
  - related uncertainty does not prevent normal verification from a task's established instructions; failed verification and missing facts still prevent allocation;
  - the plan records potentially affected task IDs in `review_warnings` and marks their summary rows provisional (`possibly_affected_tasks`: the IDs it names, else the tasks of the two messages before it, plus other requests for the same order). Raw decision statuses remain unchanged; consumers must read the warnings and summary rows;
  - a provisional recommendation still reserves queue time;
  - never present a link candidate as a confirmed link;
  - review records reserve nothing.

  Evaluate complete runs only.

## Allocation and evaluation rules to preserve

- Check workshop status, category compatibility, batch caps, requested destinations, exclusions and deadlines before selecting a workshop. The dispatcher's own workshop choice is the exception (see Dispatcher review modules).
- A deadline on or before the dispatch date is review-only (`deadline_passed`): no estimates, least-late option or queue time. Only a revised deadline that the dispatcher confirms returns it to allocation, and the original date stays on record (decision of 18 October 2026). In the dispatcher review, the dispatcher's own workshop choice also allocates it, late (decision of 20 October 2026; see Dispatcher review modules).
- Preserve the current ranking formulas and tie-breaks during refactoring. Explicit quality preference selects defect-rate-first ranking; the current hybrid has no direct defect-rate weight. Any new rule for delicate/expensive work or new weights requires a stated input, rationale and evaluation.
- A recommendation is a preview, not a committed assignment. Use a separate queue copy for planning. Review items reserve nothing; only feasible recommendations add production and expected rework to the tentative queue.
- Preserve the reference-workshop review gate (from allocation v4) for a winning workshop recorded only as a reference, and distinguish informational closest/alternative options from selected assignments. Retain source-message accounting and each run's saved input record; explicit-objective plans must not overwrite the default plan.
- Historical completed orders remain allowed in this experiment; live status checks are future work. Preserve the root instructions' separation between harness results, language interpretation and explanation evaluation.
- The graph's final approval saves the shown review as JSON; it commits no live assignment and changes no live queue. Reallocation, committed assignments and the second review are planned features: follow the [planned workflow](../docs/system-design.md#6-planned-dispatcher-review-and-reallocation) when implementing them; do not silently turn a preview into an assignment.

## Dispatcher review modules

- `dispatcher_review/dispatcher_plan.py` (notebook 06 Part 8a): `build_dispatcher_plan(run_folder, decisions)` plans a saved run again with the dispatcher's decisions and returns a draft review; `finalize_review(review)` labels a copy of the shown draft as final without planning again; `input_signature()` is a SHA-256 of the dispatch date, `orders.csv` and `workshops.csv`.
- `dispatcher_review/dispatcher_decisions.py` (notebook 06 Part 8b): `apply_answer(run_dir, decisions, review, answer)` checks one answer, applies it to a copy of the decisions and returns `(decisions, review, then, refusal)`; the decision helpers, `print_review` and `save_dispatcher_files`.
- Definitions are notebook 06's, except those listed in `CHANGED`, `NEW` and `DROPPED` in `tests/test_dispatcher_review.py` (decision of 20 October 2026, [DISPATCHER_REVIEW_GRAPH_PLAN.md](DISPATCHER_REVIEW_GRAPH_PLAN.md)): one final approval replaces per-row approve and release, so there is no `approved` reserving status, no approved-first planning and no finalize mode in `build_dispatcher_plan`; the helpers take the decisions and tasks as arguments; every refusal is a `ValueError`.
- The dispatcher decides (decision of 20 October 2026): tasks with a chosen workshop are planned first, then the other ready tasks around them, each group earliest deadline first. A chosen workshop is always used, even when it is late (status `accepted_late`), the deadline has passed (also `accepted_late`, with the original deadline in the reason) or it breaks a hard rule ("It overrides the hard rule ..." in the reason). A choice is not used for a task with missing facts, in a duplicate-order review or with a request the plan does not support (a split or an unsupported condition). `accept_late` is unchanged: it plans in deadline order and returns to review when the lateness exceeds what was accepted.
- An answer is `{"decisions": [...], "then": "review_again" | "approve_all" | "finalize"}`. Each decision is named after its helper: `correct` (`facts`, `resolves`), `choose_workshop` (`workshop_id`), `accept_late` (optional `max_days`, any finite number of days of 0 or more, sent alone except with `finalize`), `warnings_checked` (`row_ids`) and `clear`. A field the decision does not take is refused.
- An answer is all or nothing: a refused decision, or a recalculated review with `decision_problems`, refuses the whole answer and changes nothing. `approve_all` takes no decisions and approves the review last shown, without planning again. `finalize` applies the whole batch with one calculation, refuses it when accepted lateness no longer covers its task, adds `changes` (rows that differ from the review shown, `changed_rows`) and then approves like `approve_all`. A review whose input signature no longer matches refuses every answer until the inputs are restored or the chat is processed as a new run.
- `finalize_review` sets the status to `final`; each row whose outcome is a recommendation, a dispatcher's choice or accepted lateness, and which has no unchecked warning, gets outcome and decision status `approved` and `final: true`. Other rows stay unresolved. A final review is saved JSON that may keep unresolved rows, not a completed live dispatch.
- No model call is made. Only `save_dispatcher_files` writes files: `dispatcher-decisions.json` and `dispatcher-plan.json` in the run folder, each with a copy in `plan-history/`.
- `tests/test_dispatcher_review.py` is offline and runs notebook 06's Part 8 cells, which it only reads, as the reference. Run `uv run python -m unittest discover -s tests -v` after every change to these modules.

## Full pipeline graph

- `run_full_pipeline.py` runs the chat file named in `config.toml` through `app_full_pipeline/pipeline_graph.py` in one LangGraph run: processing, then a plan of the run just processed, then a pause for the dispatcher's review. It writes the same run folder as `run_intake_and_processing.py` followed by `run_allocation.py`, prints the first review and its thread ID, and stops. It can make paid model calls, so the paid-run rules above apply.
- The graph has eight nodes: notebook 05's six, then `dispatcher_review` and `save_review`. `plan_allocation` also calculates the empty decisions and the first review, so both are checkpointed before the pause. `dispatcher_review` calls `interrupt()` with the checkpointed review and any refusal, then applies the answer; `after_review` loops back to it until a valid `approve_all`, which goes to `save_review` (`finalize_review`, then `save_dispatcher_files`) and the end.
- A paused run is kept in `output/dispatcher-review-checkpoints.sqlite` by `SqliteSaver` (`langgraph-checkpoint-sqlite`), with `durability="exit"`: the state is saved when the run stops (at a pause, at the end or on an error), not after every processing step. `resume_dispatcher_review.py <thread ID>` shows the paused review; `resume_dispatcher_review.py <thread ID> <answer.json>` sends one answer. Resuming makes no model call. A finished or unknown thread has no paused review.
- Nodes hold no rules: each calls the processing, allocation or dispatcher review functions and returns only the graph-state keys it changed. Keep the graph state plain data. The node, router and graph definitions are notebook 05's, except those listed in `CHANGED` and `NEW` in `tests/test_pipeline_graph.py`: `save_outputs` always goes on to `plan_allocation` (a partial plan for an incomplete run), the LangSmith run is named `full-pipeline`, and the review loop is added.
- With `LANGSMITH_TRACING=true`, valid tracing configuration and network access, normal nonempty runs through `run_full_pipeline.py` and `resume_dispatcher_review.py` send chat text, processing state, the plan, the reviews and the dispatcher's decisions to LangSmith, including fully cached runs. Standalone allocation has no graph trace. The tests keep tracing off.
- Keep the code, the data and the dispatch date fixed while a review is paused. There is no reallocation, live commit or second review after reallocation yet; add them only by following the [planned workflow](../docs/system-design.md#6-planned-dispatcher-review-and-reallocation).
- `tests/test_pipeline_graph.py` is offline. Run `uv run python -m unittest discover -s tests -v` after every change to the graph.

## HTTP API

- `main.py` creates the FastAPI app (run `uv run fastapi dev main.py`, then open `/docs`). `fastapi_routes/runs.py` (`GET /runs`, `GET /runs/{run_id}`) reads saved run files; `fastapi_routes/dispatcher.py` (`GET /reviews/{thread_id}`, `POST /reviews/{thread_id}/answer`, `POST /reviews/{thread_id}/finalize`) answers 404 before any checkpoint file exists, and otherwise calls `paused_review` and `resume_graph` on the checkpoint file, as `resume_dispatcher_review.py` does. Decisions, alternatives and verification: [FASTAPI_BUILD.md](FASTAPI_BUILD.md), following [FASTAPI_STRUCTURE_GUIDE.md](FASTAPI_STRUCTURE_GUIDE.md).
- Routes hold no rules and make no model call: they read files or call the existing functions and return JSON. `apply_answer` checks every answer, so the answer body stays a plain JSON object and its refusal messages reach the frontend unchanged; a refused answer is a normal response with `refused` set. Do not add a route that starts processing unless the user asks: it can make paid calls.
- A thread ID is not a run ID; the thread ID comes from `run_full_pipeline.py`. There is no CORS yet (decision of 20 October 2026), no authentication and one dispatcher.
- `tests/test_fastapi_routes.py` is offline. Run `uv run python -m unittest discover -s tests -v` after every change to these files.

## Run reports

- `make_run_report.py <run folder>` writes `run_report.md` into the run folder: settings, processing counts, every plan row with its reason, and each stage's calls, tokens, cost and model time. With `--key <key.json> --data <data folder>` it adds a score against a JSON answer key. It makes no model call and changes no other run file.
- `eval_run_report/`: `run_summary.py` (counts and costs), `score_against_key.py` (matching, decisions, causes, fields, labels and links), `key_reference_plan.py` (the key's own plan by the app's rules, replacing the allocation modules' data only while it is made) and `report_markdown.py`.
- The score rules follow "How the score works" in [the test-set plan](docs/evaluation/NEW_TEST_SETS_PLAN.md). Change them only before a run is scored, never to fit a result, and record why. Keep the price table in `run_summary.py` the same as in `PROMPT_TESTING_RESULTS.md`.
- `tests/test_run_report.py` is offline and reads the 100-case key and data folder; update its paths when the key is renamed. Run `uv run python -m unittest discover -s tests -v` after every change to these files.
